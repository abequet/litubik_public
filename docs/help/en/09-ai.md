# AI assistance

AI is **optional** everywhere: LitUbik is fully usable without any AI key.

## What AI can help with

Protocol drafting, concept extraction, search-equation advice, title triage,
screening suggestions (title/abstract and full text), extraction column
design, cell prefill from PDFs, and the narrative synthesis of results.

## The rules

- **A human always decides.** AI output is a suggestion, marked as such
  (*AI* badge, job history); it never counts as a reviewer vote and is never
  applied without validation.
- **No anchoring by default, by choice.** A screening round can show the
  suggestion only after each reviewer's own vote (see *Screening*); looking
  earlier is possible but recorded, and the disclosure statement counts it.
- **Cost transparency**: batch AI actions, the title triage included, show
  an estimated cost before you launch them.
- **No oversized documents**: a stored PDF of more than 45 pages (a book, a
  thesis, a proceedings volume) is never sent to a model — it is assessed by
  hand.
- **Prompt transparency**: every prompt the app sends is readable — and
  editable per project — in *Project settings → AI prompts*.
- **Use transparency**: every billed call is written to the project's
  AI-use journal (helper, model, author, day, cost) — refusals, empty
  answers and attempts that failed before switching to another key
  included, since the provider charges for them. You read it — and turn it into
  a disclosure statement for your manuscript — on the *Reporting* page.

## Configuring providers

Keys are stored encrypted on the server:

- **Project keys** (*Project settings → AI keys*, project admin): used by
  this project, shared with its members through the app (members use the
  access, they never see the key).
- **App-wide keys** (*Administration → AI keys (app)*, superadmin): default
  for all projects without their own key.

Six providers are available: Anthropic (Claude), OpenAI (GPT), Google
(Gemini), xAI (Grok), Mistral AI, and **Local / self-hosted** — any server
speaking the OpenAI chat API. Several can be configured at once; when the
key marked *used for AI jobs* fails (no credit, outage), the next one takes
over, in that order.

## Model per task

Not every AI task deserves the same model. The app sorts them into two
tiers: **bulk** tasks (title/abstract and full-text screening, title triage,
translation, thematic-map labels, data extraction), many short calls where
speed and price matter, and **reasoning** tasks (protocol drafting, search
equations, concepts, results narrative, PRISMA report), few long calls where
judgement matters. Each provider has a default model per tier (Anthropic:
Claude Sonnet for bulk, Claude Opus for reasoning).

*Administration → AI keys (app)* and *Project settings → AI keys* both show a
**Model per AI task** table: for each task, a provider, a model and a
reasoning **effort** (low / medium / high; medium is the default and is
enough for structured review work). A task left on *inherited* follows the
app-wide routing, then the tier default of the best-ranked key. If the routed
provider has no key visible from the project, the best-ranked key is used
instead with its own tier model — nothing silently stops.

By default only project admins change the routing of a project. The switch
**Reviewers may change the AI model per task** opens it to every member,
from their own Settings page; keys stay invisible to them.

## Running a local model (Ollama, LM Studio, vLLM…)

Nothing has to leave your machine. The *Local / self-hosted* card takes the
**endpoint URL** of a server that speaks the OpenAI chat API — Ollama
(`http://localhost:11434/v1`, the default), LM Studio, vLLM, llama.cpp
server, or a gateway such as OpenRouter — and the name of a model it
serves (`llama3.1:8b`, `qwen3:8b`, `gemma3:12b`…). An API key is optional:
most local servers ignore it.

Three things to know:

- **Context window.** A full-text suggestion sends up to about 15 000
  tokens (the article text plus the protocol). Ollama's default context is
  shorter and the server cuts the text **silently**. Create a model variant
  with a larger window (`num_ctx 32768` in a Modelfile, or
  `OLLAMA_CONTEXT_LENGTH`) before using full-text features. Title/abstract
  screening and translation fit any model.
- **JSON discipline.** Every helper asks for a JSON answer. Small models
  sometimes wrap it in prose or stop early; the app then reports that the
  model did not return JSON rather than guessing. Instruction-tuned models
  of 8 B parameters and above are reliable; below that, expect retries.
- **Cost and disclosure.** Local calls are journaled like any other, at
  $0.00, under the provider name *local*. If **every** call of the project
  went to a local model, the AI disclosure form pre-fills the *safeguards*
  field with the fact that no record left the machine — written from the
  journal, never from the configured key.

**Never fall back to another provider.** In *Project settings → AI keys*, a
switch stops the automatic failover: when the key marked for AI jobs fails,
the failure is reported instead of the next key taking over. Turn it on when
the corpus must stay on your own model and an app-wide cloud key also exists.
